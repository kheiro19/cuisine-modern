# تحليل المشروع مع تجاهل ملفات `tests/`

تم تحليل ملفات المصدر والإعدادات والـ patch فقط، مع استبعاد جميع الملفات الموجودة داخل `tests/` وعدم الاعتماد عليها في التقييم.

## الملخص التنفيذي

المشروع عبارة عن تطبيق React/TypeScript لتصميم المطابخ، ويجمع بين:

- تصميم الخزائن السفلية والعلوية وخزائن الأجهزة.
- تخطيطات مستقيمة و`L` و`U`.
- معاينة ثلاثية الأبعاد باستخدام Three.js.
- توليد قائمة قص وتصنيع BOM.
- حساب التكلفة والفاتورة بالدينار الجزائري.
- إدارة الألواح، العتاد، الأرجل، الوزرات، القواعد الخشبية وأشرطة الحواف.
- قواعد حركية للأبواب والأدراج والرافعات و`Gola` و`Push-to-open`.
- نظام تدقيق هندسي يقارن النموذج الحسابي بما يتم رسمه.

البنية العامة جيدة، والأهم أن `partsEngine.ts` مصمم كمصدر مركزي للأجزاء والتكلفة والعتاد، مما يقلل اختلاف الرسم عن قائمة القص.

## المشكلات المهمة

### 1. مشكلة محتملة في القواعد

في `src/math/base.ts`:

```ts
if (isOpenCarcase(zonesOf(cab as never))) {
  return { ...NONE_BASE, ignored: 'APPLIANCE_BAY' };
}
```

التعليق يوضح أن القاعدة يجب تجاهلها عند وجود جهاز يقف على أرجله، مثل غسالة أو جلاية. لكن الشرط يعتمد على `isOpenCarcase`، والذي يبدو أنه يعني أن الخزانة تحتوي على قسم مفتوح عموماً.

هذا قد يؤدي إلى تجاهل الأرجل أو الوزرة أو القاعدة الخشبية لأي خزانة تحتوي على قسم `OPEN`، حتى لو كان ذلك القسم رفوفاً مفتوحة وليس مكان جهاز.

**الأثر:** حساب ارتفاع الجسم، الرسم، BOM والتكلفة قد تصبح خاطئة لخزائن تحتوي على رفوف مفتوحة.

**التوصية:** استبدال الشرط بفحص صريح لقسم جهاز مفتوح، مثلاً:

```ts
const isApplianceBay = zonesOf(cab).some(
  z =>
    z.kind === 'APPLIANCE' &&
    z.appliance &&
    OPEN_BAY_APPLIANCES.includes(z.appliance)
);
```

ثم استخدام `isApplianceBay` بدلاً من `isOpenCarcase`.

### 2. عدم منع تجاوز طول الجدار

في `src/math/kitchenLayout.ts`، الدالة `nextFreeX` تبحث عن أول موضع غير متداخل، لكنها لا تتحقق من أن:

```ts
positionX + width <= layout.widthMm
```

وكذلك `fitStates` يرصد التداخل بين الخزائن، لكنه لا يرصد خروج الخزانة عن حدود الجدار.

**الأثر:** يمكن وضع خزانة خارج نهاية الجدار بدون ظهور خطأ واضح.

**التوصية:** إضافة حالة مثل `OUT_OF_BOUNDS` أو تعديل `nextFreeX` ليعيد موضعاً غير صالح عند امتلاء الجدار، ثم منع الإضافة من الواجهة.

---

### 3. عدم وجود تحقق كامل من المخزون قبل التثبيت

التطبيق يسمح بتثبيت الخزانة مع وجود تحذيرات نقص بعض عناصر العتاد. يتم خصم المخزون عبر `applyConsumptionDelta`، لكن الواجهة لا تبدو وكأنها تمنع الإضافة عند نفاد الكمية.

التحقق الحالي يركز غالباً على وجود الصنف، وليس دائماً على:

- الكمية المطلوبة مقارنة بالكمية المتاحة.
- كمية الألواح والمساحة المتبقية.
- طول رول شريط الحافة.
- عدد الأرجل المطلوب.

**الأثر:** قد تصبح قيم المخزون سالبة بعد تثبيت عدة خزائن.

**التوصية:** إضافة أخطاء مانعة قبل `addCabinet`، مثل:

```ts
STOCK_SHORTAGE
EDGE_BAND_SHORTAGE
WOOD_AREA_SHORTAGE
```

مع عرض الكمية المطلوبة والمتاحة.

### 4. مشكلة محتملة في شريط الحافة

في `partsEngine.ts`:

```ts
const perPieceMm = !roll
  ? 0
  : p.edge === 'ALL'
    ? 2 * (p.widthMm + p.lengthMm)
    : p.edge === 'FRONT'
      ? p.lengthMm
      : 0;
```

الاستهلاك يُحسب اعتماداً على المقاس النهائي قبل خصم سماكة الشريط، وهذا مقبول غالباً للتقدير، لكنه لا يأخذ في الاعتبار:

- اتجاه الحافة فعلياً.
- الهدر الناتج عن قص الرول.
- بقايا الرول بعد كل عملية.
- اختلاف الحافة للقطع ذات الكمية المتعددة.

كما أن `EdgeBandRoll` موجود في السياق لكنه منفصل عن `WorkshopInventoryState`، ما يزيد احتمال اختلاف نماذج المخزون بين أجزاء التطبيق.

### 5. اعتماد الإنتاج على Proxy خاص بـ Vite

في `vite.config.ts`، مسارات `ambientcg` و`acgmedia` معرفة تحت:

```ts
server.proxy
preview.proxy
```

هذا يعمل أثناء التطوير ومع `vite preview`، لكنه لا يضمن وجود proxy عند نشر التطبيق كملفات static خلف Nginx أو CDN.

**الأثر:** تصفح الخامات الأونلاين قد يعمل محلياً ويفشل في الإنتاج بسبب CORS أو غياب مسار proxy.

**التوصية:** نقل proxy إلى backend/API مستقل أو استخدام خدمة وسيطة حقيقية في بيئة الإنتاج.

### 7. التحقق من TypeScript ضعيف

في `tsconfig.json`:

```json
"strict": false,
"noImplicitAny": false
```

هذا يسمح بمرور أخطاء مهمة، خصوصاً في مشروع هندسي يعتمد على أبعاد وأنواع كثيرة.

**الأثر:** أخطاء مثل `undefined`، أو قيم غير صحيحة للأنواع، قد تظهر وقت التشغيل بدلاً من وقت البناء.

**التوصية التدريجية:**

1. تفعيل `noImplicitAny`.
2. معالجة أخطاء النوع في ملفات `math/`.
3. تفعيل `strictNullChecks`.
4. تفعيل `strict` بعد تنظيف طبقة البيانات.

### 8. وجود `@ts-nocheck` في أدوات التدقيق

ملف `audit_cabinets.ts` في جذر المشروع يبدأ بـ:

```ts
// @ts-nocheck
```

رغم أنه ليس ملف اختبار، إلا أنه أداة مهمة للتحقق البنيوي. تعطيل التحقق النوعي فيه يقلل قيمة الأداة نفسها.

**التوصية:** نقله إلى مجلد أدوات مثل `scripts/audit/`، وإزالة `@ts-nocheck` تدريجياً أو إنشاء أنواع واضحة للـ fixtures المستخدمة فيه.

### 9. وجود اختلافات محتملة بين patch والمصدر

الملف `structural-fixes.patch` يحتوي تغييرات كبيرة تشمل:

- ألواح مفصلات للأبواب.
- تحسين دعم الرفوف.
- دعم inset.
- معالجة الرافعات.
- إصلاح زوايا L.
- إضافة `DOORS_TOO_NARROW`.
- تعديل fasteners.

لكن وجود الـ patch داخل المشروع لا يعني بالضرورة أنه مطبق بالكامل في نسخة المصدر. بعض التغييرات ظاهرة فعلاً في الملفات المقروءة، لكن لا يوجد سجل واضح يثبت أن كل أجزاء الـ patch مطابقة للمصدر الحالي.

**التوصية:** عدم إبقاء patch كمرجع غامض داخل المشروع. الأفضل:

- تطبيقه نهائياً.
- حذف الأجزاء المطبقة.
- أو توثيق commit/version واضح.
- إضافة سجل تغييرات مختصر.

## ملاحظات على منطق الزوايا

منطق `L` متقدم نسبياً، خصوصاً:

- استخدام `groupId`.
- حذف الأذرع كمجموعة واحدة.
- استخدام `frontSetbackSides`.
- تحويل الإحداثيات عبر `toFrame`.
- منع تداخل الوحدات من المستوى نفسه.

لكن توجد نقاط يجب مراجعتها يدوياً:

| النقطة | الخطر |
|---|---|
| `fitStates` يستثني الوحدات من نفس المجموعة دائماً | قد يخفي تداخلاً حقيقياً داخل مجموعة الزاوية إذا حدث خطأ في حساب الصناديق. |
| `cornerClearanceMm` يعتمد على وصول خزانة الجدار الخلفي للزاوية | قد لا يغطي كل حالات تغيير `positionZ` أو الأعماق غير الافتراضية. |
| حساب الواجهات في الزاوية | يحتاج اختبار بصري مع اختلاف العمق والسماكة، خصوصاً بين base وwall. |
| `frontSetbackSides` | قد يصحح تداخل الواجهة، لكنه لا يثبت بالضرورة صحة المسافة الفعلية بين صناديق الخزائن. |

## ملاحظات على BOM والتكلفة

التصميم جيد لأن `generateFactoryBOMReport` يستدعي:

```ts
priceCabinet(...)
```

وبذلك يكون مجموع التقرير مبنياً على نفس محرك التكلفة.

لكن توجد مخاطر تشغيلية:

| الملاحظة | الأثر |
|---|---|
| تكلفة الألواح محسوبة حسب المساحة وليس nesting فعلي | التكلفة تقديرية وليست خطة قص محسنة. |
| لا يوجد محرك تقطيع للألواح | قد تكون المساحة الإجمالية كافية نظرياً لكن القطع لا يمكن ترتيبها فعلياً على الألواح. |
| الهدر ثابت عبر `PANEL.WASTE_FACTOR` | لا يعكس شكل القطع واتجاه الحبيبات. |
| الأجهزة لا تدخل في السعر | صحيح حسب التصميم إذا كان العميل يوفرها، لكن يجب إبراز ذلك بوضوح في الفاتورة. |
| نقص المخزون يضاف إلى `issues` | لكنه لا يمنع دائماً إنشاء التصميم أو تثبيته. |

## الخلاصة

المشروع متقدم من ناحية النمذجة الهندسية، ويحتوي على أساس جيد جداً لتطبيق تصنيع مطابخ حقيقي. أقوى قرار معماري فيه هو جعل الأجزاء والتكلفة والـ BOM والرسم تعتمد على نفس النموذج.

أخطر المشاكل الحالية ليست في فكرة النظام، بل في:

1. احتمال تطبيق قاعدة الخزانة بشكل خاطئ على الأقسام المفتوحة.
2. السماح بخروج الخزائن عن حدود الجدار.
3. عدم وجود منع قوي لنقص المخزون.
4. اعتماد الخامات الأونلاين على Proxy خاص بالتطوير.
5. تضخم `App.tsx`.
6. ضعف صرامة TypeScript.

وبما أن ملفات `tests/` تم تجاهلها، فهذا التقييم مبني على كود الإنتاج والإعدادات وملف التصحيحات فقط، وليس على نتائج تشغيل الاختبارات.
